
# 🐳 Docker Learning Notes

# Module 1: Dockerfile

## 1. What is a Dockerfile?

A Dockerfile is a text file containing instructions used to build a Docker image.

A Docker image contains the application code, dependencies, libraries, and configuration required to run an application inside a container.

For example, a Python application can use a Dockerfile to package its source code and dependencies into an image.

### Docker image-building workflow

```text
Application Source Code
         |
         v
     Dockerfile
         |
         v
   docker build
         |
         v
     Docker Image
         |
         v
     docker run
         |
         v
   Docker Container
```

## 2. Dockerfile Structure

Example project structure:

```text
python-docker-app/
│
├── app.py
├── requirements.txt
└── Dockerfile
```

Example `app.py`:

```python
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello from Docker!"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
```

Example `requirements.txt`:

```text
Flask
```

Example Dockerfile:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 5000

CMD ["python", "app.py"]
```

## 3. FROM Instruction

The `FROM` instruction defines the base image for the Docker image.

Example:

```dockerfile
FROM python:3.12-slim
```

Other examples:

```dockerfile
FROM ubuntu:24.04
```

```dockerfile
FROM nginx:alpine
```

Purpose:
- Selects the starting environment.
- Provides the operating system or runtime.
- Supports building application images on top of an existing image.

## 4. WORKDIR Instruction

The `WORKDIR` instruction defines the working directory inside the image.

Example:

```dockerfile
WORKDIR /app
```

Docker creates the directory if it does not already exist.

Subsequent relative paths are interpreted relative to this directory.

## 5. COPY Instruction

The `COPY` instruction copies files and directories from the build context into the image.

Example:

```dockerfile
COPY app.py /app/
```

Copy all project files into the working directory:

```dockerfile
COPY . .
```

Copy a requirements file:

```dockerfile
COPY requirements.txt .
```

## 6. ADD Instruction

The `ADD` instruction copies files into an image and supports additional functionality, including automatically extracting supported local tar archives.

Example:

```dockerfile
ADD application.tar.gz /app/
```

For ordinary file copying, prefer `COPY`.

Use `ADD` only when its additional functionality is needed.

## 7. RUN Instruction

The `RUN` instruction executes commands during image building.

Example:

```dockerfile
RUN pip install flask
```

Install dependencies from a requirements file:

```dockerfile
RUN pip install --no-cache-dir -r requirements.txt
```

Ubuntu example:

```dockerfile
RUN apt-get update && apt-get install -y curl
```

RUN executes while building the image, not every time the container starts.

## 8. CMD Instruction

The `CMD` instruction defines the default command or arguments executed when a container starts.

Example:

```dockerfile
CMD ["python", "app.py"]
```

A Dockerfile normally has one effective CMD instruction. If multiple CMD instructions are present, the last one takes effect.

## 9. ENTRYPOINT Instruction

The `ENTRYPOINT` instruction configures the main executable of the container.

Example:

```dockerfile
ENTRYPOINT ["python", "app.py"]
```

It is useful when the container is designed to run a particular application or executable.

### CMD vs ENTRYPOINT

| CMD | ENTRYPOINT |
|---|---|
| Defines a default command or arguments | Defines the main executable |
| Easily replaced by a command supplied to `docker run` | Remains the main executable unless explicitly overridden |
| Often used to provide default arguments | Often used to define the container's main purpose |

Example:

```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
```

Running the container normally executes:

```bash
python app.py
```

## 10. EXPOSE Instruction

The `EXPOSE` instruction documents the port on which an application listens inside the container.

Example:

```dockerfile
EXPOSE 5000
```

Important: EXPOSE does not publish a port to the host machine.

To publish the port, use:

```bash
docker run -p 5000:5000 python-app
```

## 11. ENV Instruction

The `ENV` instruction defines environment variables inside an image.

Example:

```dockerfile
ENV APP_ENV=development
```

Another example:

```dockerfile
ENV PORT=5000
```

Environment variables can be accessed by the application.

Example in Python:

```python
import os

port = os.getenv("PORT", "5000")
```

## 12. ARG Instruction

The `ARG` instruction defines build-time variables.

Example:

```dockerfile
ARG PYTHON_VERSION=3.12
FROM python:${PYTHON_VERSION}-slim
```

Pass a build argument:

```bash
docker build --build-arg PYTHON_VERSION=3.12 -t python-app .
```

### ARG vs ENV

| ARG | ENV |
|---|---|
| Used during image building | Available to the image and running container |
| Can be supplied using `--build-arg` | Can be overridden using `docker run -e` |
| Not automatically available at runtime | Available at runtime |

Do not use ARG or ENV to store passwords, API keys, or other secrets. Use appropriate secret-management mechanisms.

## 13. USER Instruction

The `USER` instruction defines the user used to execute subsequent build instructions and the container's runtime process.

Example:

```dockerfile
RUN useradd --create-home appuser

USER appuser
```

Running applications as non-root users reduces security risks.

## 14. Docker Image Building Process

Build an image:

```bash
docker build -t python-app .
```

Explanation:

- `docker build`: Builds a Docker image.
- `-t`: Assigns a name or tag.
- `python-app`: Image name.
- `.`: Current directory is the build context.

List images:

```bash
docker images
```

Inspect an image:

```bash
docker inspect python-app
```

Run the image:

```bash
docker run -d -p 5000:5000 --name python-container python-app
```

List running containers:

```bash
docker ps
```

View application logs:

```bash
docker logs python-container
```

Stop the container:

```bash
docker stop python-container
```

Remove the container:

```bash
docker rm python-container
```

Remove the image:

```bash
docker rmi python-app
```

## 15. Dockerfile Best Practices

1. Use trusted and maintained base images.
2. Prefer lightweight images where appropriate.
3. Use a `.dockerignore` file.
4. Avoid installing unnecessary packages.
5. Combine related RUN commands where appropriate.
6. Use COPY instead of ADD for ordinary file copying.
7. Run applications using a non-root user.
8. Avoid storing secrets inside Dockerfiles.
9. Use specific image tags instead of relying on `latest`.
10. Keep the image size as small as practical.
11. Separate build-time dependencies from runtime dependencies when appropriate.
12. Organize Dockerfile instructions to make effective use of build caching.

Example `.dockerignore`:

```text
.git
.venv
__pycache__
*.pyc
.env
node_modules
```

# Module 2: Docker Networking

## 1. What is Docker Networking?

Docker networking allows containers to communicate with one another, the host machine, and external networks.

It is important when building multi-container applications.

For example:

```text
        Host Machine
             |
        Docker Network
          /       \
         /         \
   Frontend       Backend
   Container      Container
                      |
                  Database
                  Container
```

## 2. Bridge Network

The bridge network is the default network driver for standalone Docker containers.

Containers connected to the same bridge network can communicate with one another.

Check existing networks:

```bash
docker network ls
```

Run a container using the default bridge:

```bash
docker run -d --name nginx-container nginx
```

Inspect the default bridge:

```bash
docker network inspect bridge
```

## 3. Host Network

Host networking allows a container to use the host network namespace.

Example:

```bash
docker run --network host nginx
```

Important:
- The container shares the host network namespace.
- Port publishing with `-p` is unnecessary and ignored in host mode.
- Network isolation is reduced.
- Availability and behavior vary by operating system and Docker environment.

## 4. None Network

The none network disables normal external network connectivity for a container.

Example:

```bash
docker run -d --network none --name isolated-container nginx
```

Inspect the container:

```bash
docker inspect isolated-container
```

This is useful when a container should not communicate over a normal Docker network.

## 5. Custom Bridge Network

A custom bridge network provides better isolation and automatic DNS resolution between connected containers.

Create a network:

```bash
docker network create my-network
```

Run a container:

```bash
docker run -d --name app1 --network my-network nginx
```

Run another container:

```bash
docker run -d --name app2 --network my-network nginx
```

Inspect the network:

```bash
docker network inspect my-network
```

## 6. Port Mapping

Port mapping allows external clients to access services running inside containers.

Syntax:

```bash
docker run -p HOST_PORT:CONTAINER_PORT IMAGE
```

Example:

```bash
docker run -d -p 8080:80 nginx
```

Explanation:

- Host port: 8080
- Container port: 80

Access the application:

```text
http://localhost:8080
```

Check published ports:

```bash
docker ps
```

## 7. Container-to-Container Communication

Containers on the same custom bridge network can communicate using their container names.

Example:

```bash
docker network create app-network
```

Start a database container:

```bash
docker run -d \
  --name database \
  --network app-network \
  -e POSTGRES_PASSWORD=example \
  postgres:16
```

Start a client container:

```bash
docker run --rm -it \
  --network app-network \
  postgres:16 \
  psql -h database -U postgres
```

The client can resolve `database` through Docker's network DNS.

Use test credentials only in this example. Do not use real production passwords in command history or source control.

## 8. DNS Resolution Between Containers

Docker provides automatic DNS resolution for container names on custom networks.

Example:

```bash
docker run -d --name web --network app-network nginx
```

Run a temporary container to resolve the name:

```bash
docker run --rm --network app-network busybox nslookup web
```

This works when the containers share a suitable user-defined network.

## 9. Network Inspection

List networks:

```bash
docker network ls
```

Inspect a network:

```bash
docker network inspect app-network
```

Inspect a container's network configuration:

```bash
docker inspect web
```

Display network-related information:

```bash
docker inspect --format '{{json .NetworkSettings.Networks}}' web
```

## 10. Creating and Removing Networks

Create a network:

```bash
docker network create my-network
```

Connect a container:

```bash
docker network connect my-network web
```

Disconnect a container:

```bash
docker network disconnect my-network web
```

Remove a network:

```bash
docker network rm my-network
```

Remove unused networks:

```bash
docker network prune
```

# Module 3: Docker Volumes and Storage

## 1. What is Docker Storage?

Docker storage manages data used by containers and applications.

Containers have a writable filesystem layer, but this layer is associated with the container's lifecycle.

Data that must survive container removal should be stored using persistent storage.

## 2. Container Filesystem

A Docker image consists of read-only layers.

When a container is created, Docker adds a writable layer on top.

```text
       Container
           |
    Writable Layer
           |
      Image Layers
           |
      Base Image
```

Changes stored only in the writable layer can be lost when the container is removed.

## 3. Why Containers Need Persistent Storage

Applications frequently need to retain:

- Database records.
- Uploaded documents.
- Application-generated files.
- Logs.
- Configuration and shared data.

Persistent storage helps preserve this data beyond the lifecycle of an individual container.

## 4. Docker Volumes

Volumes are managed by Docker and are a recommended way to persist application data.

Create a volume:

```bash
docker volume create app-data
```

List volumes:

```bash
docker volume ls
```

Inspect a volume:

```bash
docker volume inspect app-data
```

Run a container using the volume:

```bash
docker run -d \
  --name volume-container \
  -v app-data:/data \
  nginx
```

The volume is mounted at `/data` inside the container.

## 5. Bind Mounts

Bind mounts connect a specific directory or file on the host to a location inside the container.

Example:

```bash
docker run -d \
  --name bind-container \
  -v "$PWD/html:/usr/share/nginx/html" \
  nginx
```

Changes in the host directory are visible inside the container.

Bind mounts are useful for development workflows.

## 6. tmpfs Mounts

A tmpfs mount stores data in memory rather than persistent disk storage.

Example:

```bash
docker run -d \
  --name tmpfs-container \
  --tmpfs /app/temp \
  nginx
```

Data stored in tmpfs is temporary and disappears when the container stops or is removed.

## 7. Creating Volumes

Create a volume:

```bash
docker volume create database-data
```

Use the volume:

```bash
docker run -d \
  --name postgres-db \
  -e POSTGRES_PASSWORD=example \
  -v database-data:/var/lib/postgresql/data \
  postgres:16
```

## 8. Inspecting Volumes

List volumes:

```bash
docker volume ls
```

Inspect a specific volume:

```bash
docker volume inspect database-data
```

Display volume information associated with a container:

```bash
docker inspect postgres-db
```

## 9. Removing Volumes

Remove a volume:

```bash
docker volume rm database-data
```

Docker normally prevents removal of a volume that is still in use.

Remove unused volumes:

```bash
docker volume prune
```

Warning: Removing volumes can permanently delete application data. Inspect and back up important data before removal.

## 10. Sharing Data Between Containers

Multiple containers can mount the same Docker volume.

Create a volume:

```bash
docker volume create shared-data
```

Start the first container:

```bash
docker run -d \
  --name writer \
  -v shared-data:/shared \
  alpine \
  sh -c 'echo "Hello from container one" > /shared/message.txt && sleep 3600'
```

Start the second container:

```bash
docker run --rm \
  --volumes-from writer \
  alpine \
  cat /shared/message.txt
```

Expected output:

```text
Hello from container one
```

This demonstrates how persistent storage can be shared between containers.

### Docker Storage Comparison

| Storage type | Location | Persistence |
|---|---|---|
| Container writable layer | Container filesystem | Tied to container lifecycle |
| Volume | Docker-managed storage | Survives container removal |
| Bind mount | Host filesystem | Survives container removal |
| tmpfs | Memory | Temporary |

# Module 4: Docker Compose

## 1. What is Docker Compose?

Docker Compose is a tool used to define and manage multi-container applications using a YAML configuration file.

It allows developers to configure multiple services, networks, volumes, and environment variables in one place.

## 2. Why Do We Need Docker Compose?

Consider an application with three components:

- React frontend.
- Python backend.
- PostgreSQL database.

Without Docker Compose, developers need to create and configure each container separately.

Docker Compose allows these services to be configured together.

## 3. Docker Compose Architecture

```text
            Docker Compose
                  |
             compose.yaml
                  |
       -----------------------
       |          |          |
    Frontend   Backend    Database
    Container  Container  Container
       |          |          |
       ---------- Network ----
                  |
              Volumes
```

## 4. Understanding YAML Files

YAML is a human-readable data serialization format commonly used for configuration.

Example:

```yaml
name: my-application

services:
  web:
    image: nginx
    ports:
      - "8080:80"
```

Important YAML rules:

- Use spaces for indentation.
- Do not use tabs for indentation.
- Use key-value pairs.
- Lists use hyphens.
- Indentation determines structure.

## 5. Creating docker-compose.yml

Create a project directory:

```bash
mkdir compose-demo
cd compose-demo
```

Create a file:

```bash
nano compose.yaml
```

Add:

```yaml
services:
  web:
    image: nginx:alpine
    container_name: compose-web
    ports:
      - "8080:80"
```

Note: `compose.yaml` is the current preferred Compose filename. `docker-compose.yml` is also commonly supported.

## 6. Defining Services

A service defines an application component that Compose runs.

Example:

```yaml
services:
  frontend:
    image: nginx:alpine

  backend:
    image: python:3.12-slim

  database:
    image: postgres:16
```

Each service can have its own image, build configuration, ports, environment variables, networks, and volumes.

## 7. Configuring Ports

Example:

```yaml
services:
  web:
    image: nginx
    ports:
      - "8080:80"
```

The host port is 8080 and the container port is 80.

## 8. Configuring Environment Variables

Example:

```yaml
services:
  backend:
    image: python:3.12-slim
    environment:
      APP_ENV: development
      PORT: "5000"
```

Environment variables can also be loaded from an environment file:

```yaml
services:
  backend:
    env_file:
      - .env
```

Do not commit real secrets or production credentials to GitHub.

## 9. Configuring Networks

Example:

```yaml
services:
  frontend:
    image: nginx
    networks:
      - app-network

  backend:
    image: python:3.12-slim
    networks:
      - app-network

networks:
  app-network:
    driver: bridge
```

Services connected to the same Compose network can communicate using service names.

## 10. Configuring Volumes

Example:

```yaml
services:
  database:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: example
    volumes:
      - postgres-data:/var/lib/postgresql/data

volumes:
  postgres-data:
```

This provides persistent database storage.

## 11. Starting Multiple Containers

Start all services:

```bash
docker compose up
```

Start in detached mode:

```bash
docker compose up -d
```

Build images and start services:

```bash
docker compose up --build -d
```

## 12. Stopping Services

Stop running services:

```bash
docker compose stop
```

Stop and remove containers and networks created by Compose:

```bash
docker compose down
```

Remove containers, networks, and associated named volumes:

```bash
docker compose down -v
```

Warning: `-v` can delete persistent application data.

## 13. Rebuilding Containers

Rebuild service images:

```bash
docker compose build
```

Rebuild and start services:

```bash
docker compose up --build -d
```

Recreate containers:

```bash
docker compose up -d --force-recreate
```

## 14. Viewing Logs

Display logs from all services:

```bash
docker compose logs
```

Follow logs:

```bash
docker compose logs -f
```

Display logs from a specific service:

```bash
docker compose logs backend
```

Display the latest 50 log lines:

```bash
docker compose logs --tail=50
```

## 15. Scaling Services

Scale a service:

```bash
docker compose up -d --scale backend=3
```

Important:
- The service should not have a fixed `container_name` when scaling.
- Published host ports must not conflict between replicas.
- Scaling is not the same as production orchestration.
- Some deployment environments require a separate orchestration platform.

## 16. Useful Docker Compose Commands

| Command | Purpose |
|---|---|
| `docker compose up` | Start services |
| `docker compose up -d` | Start services in background |
| `docker compose down` | Stop and remove services |
| `docker compose stop` | Stop services without removing them |
| `docker compose start` | Start stopped services |
| `docker compose ps` | List Compose containers |
| `docker compose logs` | View service logs |
| `docker compose build` | Build images |
| `docker compose pull` | Download service images |
| `docker compose config` | Validate and display Compose configuration |
| `docker compose exec` | Execute a command in a running service |
| `docker compose restart` | Restart services |
